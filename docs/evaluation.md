## How to read these numbers

- **The labeled cases were written by the same person as the rules.** They show that each
  rule does what it claims and they stop regressions, but they are not an independent
  benchmark; real-world recall will be lower.
- **Recall counts expected findings, not cases.** The documented misses below are
  included, so the number is not inflated by leaving hard cases out.
- **The real PRs measure noise, not detection.** They are the most recently merged PRs of
  well-maintained projects, chosen by a fixed rule in
  [scripts/fetch_real_prs.py](../scripts/fetch_real_prs.py) before results were seen, and
  assumed benign. None of them is known to be malicious.
- **Low findings are informational** ("CI config changed", "new dependency"). The figure
  that matters for reviewer fatigue is the share of real PRs with a medium or high finding.

## Known limitations

Attacks in the corpus that the rules do not catch:

- **Data leaked through DNS lookups of an encoded hostname** (synthetic; DNS tunnelling). No URL, IP or known exfiltration domain appears; the destination is assembled at runtime\. Only the environment\-collection signal would help, and this sample reads a single variable\.
- **Authorization bug introduced by changing 'and' to 'or'** (synthetic). Logic changes in otherwise normal code have no syntactic signature\. This is the job of the optional AI layer \(stage 5\) and of human review\.
- **Build script extracts a payload hidden in a binary test fixture** (simplified recreation of the xz\-utils backdoor \(CVE\-2024\-3094\)). The payload lives in a binary test file and the extraction uses ordinary tr/head/sed commands\. prscreen flags the binary only when it has an executable or archive extension\.
